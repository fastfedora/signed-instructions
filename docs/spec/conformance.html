Conformance

Conformance is demonstrated with test vectors. A verifier that produces the expected status for every vector, and a signer whose output the reference verifier accepts, conform to SIB/1. The vectors are generated by the reference implementation and checked against its verifier before they are written, so they are known-good by construction.

Requirements by Target

Signer
Produces blocks that the reference verifier reports as verified with the signer’s registry entry, for instructions under both text/1 and raw/1, including instructions containing typographic quotes, non-breaking spaces and multiple lines. Shows the canonical instruction and the header terms before signing. Emits a visible dev-mode warning for a software key.
Verifier
Produces the expected status for every vector below. Applies the steps of Verification in order. Carries the block’s claims on every failing result. Emits the manifest schema for a document containing several blocks, some failing, in discovery order.
Harness
Runs the verifier before its permission decision on every tool call. Delivers the manifest on a channel the agent cannot write to. Fails closed when the verifier or the classifier fails. Records the manifest for each decision.

Vector Format

The vectors live in docs/spec/vectors/, one JSON file each, listed in index.json. Each file holds:

{
  "name": "expired",
  "note": "why this vector exists",
  "block": "-----BEGIN SIB SIGNED INSTRUCTION-----\n...",
  "registry": {"signers": [{"signer": "alice@example.com", "keys": [ ... ]}]},
  "inputs": {"now": "2026-09-13T12:00:00Z", "audience": "acme/dev-agent", "mode": "dev"},
  "expected_status": "expired",
  "expected_text": "canonical instruction, or null when the rule is unknown"
}

A verifier under test is given block, registry and inputs, with a nonce store that accepts everything, and MUST produce expected_status. Where expected_text is not null it MUST also report that canonical text. The generator, docs/spec/vectors/generate.py, creates a fresh dev key on every run, so signatures differ between runs and statuses do not.

Vectors

Vector Expected status What it checks
verified verified The block as signed.
verified_after_transport verified Quoted with > and one line re-wrapped; the canonical text is unchanged.
invalid_signature invalid_signature One word of the instruction changed after signing.
metadata_mismatch metadata_mismatch A clear metadata line edited; the signed header is intact.
expired expired now is after exp.
not_yet_valid not_yet_valid Issued more than 60 seconds after now.
audience_mismatch audience_mismatch Block audience acme/ci-agent presented to acme/dev-agent.
unknown_signer unknown_signer Signer not in the registry.
unknown_key unknown_key Signer is enrolled, this kid is not.
unknown_key_wrong_signer unknown_key An enrolled kid used with a different iss.
dev_key_in_enforced_mode dev_key_in_enforced_mode The verified block, verifier in enforced mode.
malformed_not_detached malformed A payload segment is present; a block must be a detached JWS.
malformed_unknown_canon malformed The header names a canonicalization rule the verifier does not know.
revoked revoked The key is marked revoked in the registry.

nonce_replayed has no vector in Phase 1, because the reference nonce store accepts every block. A vector is added with the store in Phase 3.

Running the Vectors

Against the reference verifier:

.venv/bin/python docs/spec/vectors/generate.py

The script regenerates and checks every vector; a failed assertion names the vector and the status produced. A third-party verifier reads the JSON files directly.
